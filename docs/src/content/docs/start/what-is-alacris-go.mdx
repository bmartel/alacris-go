alacris-go renders [alacris](https://bmartel.github.io/alacris/) web components
from Go and [templ](https://templ.guide). It is three layers, each usable on
its own.

## What Go actually renders

A component's shadow content is produced by its `setup()` function when the
element connects, **in the browser**. There is no server-side rendering of
component internals, and alacris does not support declarative shadow DOM.

So what a Go server renders is the element itself:

<GoExample id="slots" title="What the server produces" />

Two consequences:

- **Slot content is real HTML in the document.** It is in the first paint and in
  a crawler's view of the page. Put content that matters for SEO, or for readers
  with JavaScript disabled, here.
- **Everything inside the shadow root appears when the module loads.** Between
  first paint and that moment the element is present but empty.
  [`alacris.Pending`](/alacris-go/guides/rendering/#hiding-elements-until-they-are-defined)
  hides it until then.

<Aside type="caution" title="If you need the component's internals in the HTML">
  You need a different tool. alacris-go will not render them. What it will do is
  make the parts a server *can* own (props, slot content, and state) type-safe.
</Aside>

## Why every prop can cross as an attribute

alacris coerces an attribute using the **type of the prop's default** in
`define()`. Look at what that means for an object default:

```js
// define.js
const coerce = (v, d) => {
  if (v === null) return typeof d === 'boolean' ? false : d;
  const t = typeof d;
  if (t === 'number') return +v;
  if (t === 'boolean') return v !== 'false';
  if (d !== null && t === 'object') { try { return JSON.parse(v); } catch { return d; } }
  return v;
};
```

`JSON.parse` is the object path. **Objects and arrays round-trip through
attributes**, so a fully-formed component needs no post-load property
assignment and no hydration payload:

The page is complete before any JavaScript has run.

## The three layers

| Layer | What it does | What it costs |
| --- | --- | --- |
| [`alacris`](/alacris-go/guides/rendering/) | Render elements, serve the runtime. | Nothing. Ordinary request/response. |
| [`gen` + CLI](/alacris-go/guides/codegen/) | Typed Go wrappers from your `define()` calls. | A generate step, next to templ's. |
| [`live`](/alacris-go/guides/live-props/) | Server-driven props and component events. | A stateful server and session affinity. |

Most applications want the first two. Use the third when the server owns what
the page shows (a shared board, a dashboard, a queue) and you would otherwise
be writing polling or a custom WebSocket protocol.

The module's example is that third layer in a page: `examples/todo` is a live
Kanban board (lanes, cards, members, labels) whose chrome is Alacris UI and
whose state lives on the server. Two windows stay in step because a move is
one property write.

```bash
go run ./examples/todo
```

## What this is not

- **Not a component framework.** Component internals are JavaScript, because
  `setup()` runs in a browser. alacris-go does not invent a Go DSL for
  templates and signals.
- **Not a replacement for htmx or Datastar.** Those swap HTML. This writes
  properties, which is a smaller and more precise operation, but only works for
  state a component already models as a prop.
- **Not tied to the live layer.** The first two layers are stateless and have no
  dependency on the third.
